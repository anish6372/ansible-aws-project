# Design notes

Grouped by Well-Architected pillar. Each row says what I chose and what it cost me.

## Security

| Choice | Why | Trade-off |
|---|---|---|
| No SSH; SSM Session Manager instead | No inbound admin port, no keys to manage, sessions are logged | Ansible over SSH for dev still needs `enable_ssh` and a /32 |
| App SG accepts port 80 only from the ALB SG (prod) | Instances cannot be reached directly even though they have public IPs | Debugging goes through SSM |
| Egress limited to 80, 443 and 5432 | Less room for data exfiltration | A new outbound protocol needs a rule |
| IMDSv2 required, encrypted gp3 root volume | Blocks SSRF credential theft; encryption at rest | None that I noticed |
| RDS password generated by RDS and stored in Secrets Manager | Never in code or Terraform state | The app has to read it at boot |
| RDS in private subnets, ingress from the app SG only | SG-to-SG reference instead of a CIDR | App and DB must share a VPC |
| CI authenticates with GitHub OIDC and a read-only role | No long-lived AWS keys; CI cannot change infra | Apply is manual |
| Service runs as a no-login user under systemd sandboxing; secrets in a 0600 env file | Least privilege | A bit more Ansible |
| Downloads are checksum-pinned (Node, node_exporter) | Supply-chain integrity | Checksums change on every upgrade |
| Trivy, Checkov, Gitleaks and Dependabot in CI | Catch misconfigurations, CVEs and leaked secrets early | Some findings need a documented ignore, see `.trivyignore` |

### The no-NAT decision

The prod instances are in public subnets with public IPs. A NAT gateway is about $32 a month and I have a small
budget. The instances need outbound access at boot (apt, pip, S3, Secrets Manager, the Node download), so without
NAT they need a public address. What keeps them closed is the security group: only the ALB can reach port 80.
With a bigger budget I would move them to private subnets behind NAT, or use VPC endpoints for S3 and Secrets
Manager. `enable_nat` is already a switch in the network module.

## Reliability

| Choice | Why | Trade-off |
|---|---|---|
| ASG across 2 AZs, min 2, ELB health checks, 600s grace | One AZ or one instance can fail without an outage | Double the compute |
| Rolling instance refresh when the launch template changes | Deploys without downtime | A broken build can stall the refresh (it did once, see the README) |
| `/health` is liveness only; `/api/status` checks the DB | A database blip does not make the ALB kill healthy instances | Two endpoints |
| Graceful SIGTERM handling, systemd `Restart=on-failure` | Clean deploys, self-healing | |
| RDS single-AZ, 1-day backups on prod; Multi-AZ is a switch | Free-tier limits, and Multi-AZ doubles the cost | The database is a single point of failure |

## Cost

| Choice | Why |
|---|---|
| Expensive parts are variables (`enable_nat`, `enable_rds`, `high_availability`, `rds_multi_az`, `enable_flow_logs`) | One codebase covers a $0.02/hour dev setup and a prod-like demo |
| Prod is applied, checked and destroyed | Nothing idles overnight |
| Infracost on PRs (optional) | The cost change is visible in review |

See [cost.md](cost.md) for the numbers.

## Operations

- Everything is in code. Remote state is in S3 with versioning and native locking (`use_lockfile`).
- PRs get a Terraform plan comment; apply is manual.
- Pre-commit runs fmt, lint and secret scanning locally.
- The app logs JSON. CloudWatch has five alarms (unhealthy hosts, ALB 5xx, ASG CPU, RDS CPU, RDS free storage)
  that publish to an SNS topic, plus a dashboard with requests, healthy targets, fleet CPU and RDS metrics.

## Performance

- t3.micro behind nginx, connection pool of 5 with timeouts, gp3 volumes.
- The ASG scales out on CPU target tracking. I have not load-tested it, so the thresholds are defaults.

## Gaps

- HTTPS is written but not applied (needs a domain).
- No automated app deploy pipeline; a change rolls the instances through Terraform.
- No load test, so I cannot say where it falls over.
- The CI workflows have not run yet.
